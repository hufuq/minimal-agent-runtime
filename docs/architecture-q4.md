# 架构设计题 · 第 4 题：Agent 的幂等性与重试设计

> 题目：LLM 输出是非确定性的，工具调用可能超时。重试一次工具调用时，怎么保证不产生副作用（比如重复下单）？如何让 agent 框架感知"这个工具是幂等的"？

## 一、问题本质：三个不确定性叠加

这道题难在三个不确定性是叠加在一起的：

1. **LLM 非确定性**：同一个用户意图，模型可能多次生成相同的工具调用（幻觉重复），也可能参数略有差异。
2. **超时歧义**：工具调用发出去但没等到响应，调用方不知道下游到底执行了没有——这是分布式里最经典的"两军问题"。
3. **副作用不可逆**：写操作（下单、扣款、发消息）一旦重复执行就是资损或脏数据，而查询类操作重复一万次也无妨。

所以盲目重试会重复下单，一律不重试可用性又太差。我的方案分三层：**工具注册时声明幂等性、每次调用携带幂等键并维护状态机、Runtime 按状态决策重试还是交还模型**。

## 二、第一层：工具元数据声明，让框架"感知"幂等

框架无法靠猜知道一个工具是否幂等，必须在注册时显式声明。我在工具 Schema 里加两个字段：

```json
{
  "name": "create_order",
  "description": "创建订单",
  "idempotent": false,
  "retry": {"maxAttempts": 0, "backoffMs": 0}
}
```

约定两条默认规则，减少工具开发者的遗漏：

- **读操作默认幂等**（query/get/list 命名开头），允许自动重试，比如最多 3 次、指数退避；
- **写操作默认非幂等**，`maxAttempts = 0`，禁止框架自动重试，除非开发者显式打开。

工具开发者最懂自己的接口语义，由他在注册时显式声明，比框架事后推断可靠得多。这和 HTTP 语义里 GET 幂等、POST 非幂等是同一个思想。

## 三、第二层：幂等键（callId）+ 状态机，解决"能不能重试"

声明了幂等性还不够——就算工具允许重试，重试也不能让下游再执行一遍。核心手段是**每次工具调用生成全局唯一的 callId，全链路传递，下游以 callId 为幂等键**。

### 1. callId 的生成与传递

LLM 决定调用某个工具后，由 Runtime（不是模型）生成 `callId = sessionId + toolName + 参数指纹 + 短随机串`，随请求传给下游业务接口。参数指纹（args 排序后的 hash）让"模型幻觉重复生成相同调用"也能得到相同或可追溯的标识。

### 2. 三态状态机

每次调用在存储（Redis 即可）中维护一个状态：

```
PENDING（已发起，执行中）──→ SUCCESS（执行成功，缓存结果）
                     └──→ FAILED（明确失败，允许决策重试）
```

Runtime 重试前**先查状态，而不是直接重发**：

- **SUCCESS**：下游其实执行成功了，只是响应丢了。直接取缓存结果返回，**绝不重复执行**——这就解决了超时歧义；
- **PENDING**：上次调用还在执行，不能并发重发，等待或稍后再查；
- **FAILED**：回到第一层，查工具元数据——幂等工具按策略重试，非幂等工具不重试。

### 3. 下游业务侧的兜底

callId 能拦住的只是"框架层面的重试"，真正的幂等必须落在业务侧：

- 数据库唯一约束（如 `order_no` / `callId` 唯一索引），重复插入直接失败转成功返回；
- 业务接口收到重复 callId，返回首次执行的结果而不是报错，让 Agent 拿到正常响应继续走。

这套思路我在电商秒杀项目里落地过：下单接口用预生成的幂等号做防重，消费端用业务唯一键防重复建单。Agent 场景的区别在于——**调用方从确定性的代码变成了非确定性的 LLM，重复调用的概率高得多，所以幂等和重试策略必须收敛到框架层统一做，而不是每个业务自己写一遍**。

## 四、第三层：Runtime 决策逻辑与降级

把前两层串起来，Runtime 的完整决策流：

```
LLM 输出工具调用
  → Runtime 生成 callId
  → 查状态机
      SUCCESS → 返回缓存结果（防幻觉重复调用）
      PENDING → 等待/轮询
      不存在  → 置 PENDING，发起调用
  → 调用成功 → 置 SUCCESS，结果回灌模型
  → 调用失败/超时歧义 → 置 FAILED（或保持 PENDING 待对账）
      幂等工具   → 按 retry 策略自动重试（带退避，达上限停止）
      非幂等工具 → 禁止自动重试，把失败信息回灌给模型
```

非幂等工具失败后，决策权交还给模型：由模型向用户确认——"刚才下单请求超时了，我不确定是否成功，要我帮你查一下订单状态，还是重新发起？"用户确认后生成**新的 callId** 再执行。这是最后的、也是最可靠的兜底：**把不可逆操作的最终确认权留给人类**。

## 五、边界与工程细节

1. **幻觉重复调用**：模型在多轮 loop 里可能再次输出一模一样的工具调用。靠 callId 参数指纹在短期窗口内去重，直接返回首次结果。
2. **幂等记录的存储与 TTL**：Redis key `agent:idempotent:{callId}`，TTL 对齐业务防重窗口（如下单场景 24h），过期自动清理不撑内存。对账级别要求的场景落数据库。
3. **重试的退避与熔断**：指数退避 + 上限；下游持续 5xx 时熔断降级，避免 Agent  loop 把故障下游打爆。
4. **与 MQ at-least-once 的关系**：如果工具调用走 MQ 异步，消费端仍需独立幂等（唯一键），callId 贯穿同步与异步两段。
5. **观测性**：callId 进 trace 日志，一次"模型决策 → 工具调用 → 重试 → 最终结果"可全链路回放，这也是排查"到底下没下单"的依据。

## 六、总结

一句话概括我的设计：**用 `idempotent` 元数据让框架感知工具语义，用 callId 状态机消解超时歧义和幻觉重复，用"非幂等工具失败交还模型/用户"兜住最后一道防线**。幂等性最终锚定在下游业务的唯一约束上，框架层做的是"不制造重复、不放大故障"。
